Broadly speaking, current vulnerability detection methods face two major challenges:
1. **Low Precision**: Current static methods (including LLM-based methods) still have high FPs
2. **Low Recall**: When applied current tools to real projects, they struggle to detect real vuls.

This two challenges seem to be solved by using concolic execution methods, as explained:
1. A higher precision is expected: using concolic execution, each reported warning will equipped with a proof that it can be triggered, the FPs can be easy eliminated by using solvers or LLMs.
2. A higher recall is less clear: Using concolic execution can somewhat ignore classical src/sink definitions, if the concolic modeling process is efficient and capable.

Here already have some warning filtering methods: `LLM4PFA`
It filters warnings generated by existing static analysis tools (e.g., codeql): 
>given a warning function call trace and a vulnerable variable, it will model and solve each function in the trace, if one function of the function trace is infeasible, it will be treated as a FP.

This method is limited in two aspects:
1. It only support limited programming languages and CWE-types: NPD, UAF, BOF  in C/C++. So basically, most of them are numeric values. And the status it need to care is also simple: NULL, release and index.
2. Starting from existing warnings, it can not improve the **recall** of current methods.

So concolic a project and detect some vuls seems promising?
While I think there are at least two questions to solve:
>Q1. First and foremost, where to start? When given a project(especially a lib), you don't know where is the main logic and how them are connected. Find a start or starts is challenging.

Face this question, I think here are 3 potential solutions:
1. Like they solve SWE-bench, we can equip LLMs with tools to inspect specific files and dirs. To judge which are potential vulnerable files, and start to explore.
2. Using existing tests, explore the function call traces
3. Using existing vul reports

>Q2. The complexity of modeling and solving.
	To support different CWE types, should model different aspects (e.g., for NPD you should care about NULLs, for XSS, you should care about input to output, for OOB, should care about numeric values)
	And the solving process is also consuming, use LLM to replace some time-consuming solves, and can reduce the path by some ways (break hypothesis, compress function call paths...)

Face this question, I think some novel ideas may help:
1. for vul detection scenario, the path may be reduced.
2. for different, may let LLM give different malicious hypothesis input, break the solving process when they are not satisified.
