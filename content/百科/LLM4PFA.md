## Target
Obviously, LLM4PFA aims to **filter infeasible warnings** generated by SATs (e.g., CodeQL). 
## Method
### Extract Constraints
It judge the feasibility by considering the critical conditional statement (e.g., branching, loop, goto/return):
- **Within a function:** For start and exit in the warning, start -> exit is feasible, iff there is a path that conditions along it can be solved & no extra goto or early return.
- **Inter functions:** The connection between functions are built by function call. There will have some specific program status proceed this call in the caller function, and part of the status is treated as pre-condition of the callee function.
So, for a bug report consisted of a chain of function calls, it is feasible iff each function is feasible (the callee is constrained by the caller.)
### Solving
For each var in conditions, it employs Z3 to solve the symbolic range when it is executed. The program status is related to the bug-type (e.g., for NPD, just NULL and !NULL).
For function call inside the conditions, it find the called function and iteratively find and reason the symbolic range of the return value.
## Pros
- Solve the feasibility issue in some extend.
- Good performance
- Exec free.
## Cons
- Scope limited: only conditions.
- Range limited: the program states passing through functions only about the vul-type.
- Solve limited: the range of function call is reasoned by LLMs, and no formal things, just prompts.
